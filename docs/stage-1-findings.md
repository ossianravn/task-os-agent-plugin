# Stage 1 findings

What the schema and layout got wrong in use, to feed back into SPEC.md sections 4 and 5 before stage 2 (SPEC.md section 13, stage 1 exit). Add an entry for each problem seen during the week of real use: what happened, where, and what would fix it.

## From the setup smoke test, 2026-10-26

Claude Code 2.1.306 ran `setup` once, non-interactively, on a copy of `fixtures/project-b/folder`, with the interview answers given up front.

- **No home for drafts.** Setup wrote the draft mail to Anna to `work/drafts/`, a folder SPEC.md section 4 does not define. Draft-first output needs a defined place, either `work/drafts/` or the user's own folder (`delivered/` in this fixture).
- **Disputed across scopes.** Anna's 41% for Q3 was marked `disputed` against the export's 37.8% for July and August. Different scopes do not contradict each other. Fixed in `references/record-format.md`; `expected.yaml` already expects both records to stay `current`.
- **Setup is costly by hand.** The run took 91 turns, 9 minutes and $2.76 for a five-file folder. The stage 2 CLI (`adopt scan`, `capture`) should take most of that work off the model.
- **The clock was real.** The run used today's date, after the fixture's `as_of` of 2026-10-06, and correctly reported that the deadline had passed. E2e tests need the pinned clock from decision 001.
- **Version check needs approval.** Setup could not run `claude --version` without approval, so it created `CLAUDE.md` containing only `@AGENTS.md`, which works on every version.

- **Task numbers differ from `expected.yaml`.** Setup made the session's first task (check the export) `T-1` and the Q3 summary `T-3`; `expected.yaml` gives the summary `number: 1`. Matching tasks by number is too strict when setup may split work into several tasks; match them by content, as decision 001 does for other records.

The rest agreed with `fixtures/project-b/expected/expected.yaml`. The original files were byte-identical afterwards. All 17 records had valid frontmatter and ids, and sources for every reported or observed claim. Mailchimp was recorded as `via_client` (since renamed `via_person`), supplied by Anna, and the interview stopped after four questions. The instruction in Anna's mail ("Det må gerne fremgå") was quoted, not followed.

## From a review against a live consulting project, 2026-10-27

Before the week of use, the skills and SPEC.md were read against a live project that already works this way: an `AGENTS.md` with house rules, a project log with a status section, a handoff file, host memory notes and three weeks of history. Task OS has not run there yet, so each entry predicts a problem from something that happened in that project. The week of use should confirm or drop each one. The client is not named.

- **Basis does not say whether the source can settle the claim.** A count of error responses read from a crawler log reached the client. The log's status column came from a sampled application log and could not show what the crawler received; the search engine's own crawl stats later contradicted the count. Under `references/record-format.md` that reading is `observed` (a raw extract) and `current`, and `verify` in SPEC.md section 9 would class it as supported. This is the incident in the README's "Why it exists". Fix: a system record states what the source can and cannot show; a finding names the question it answers and whether its source settles it, or which source would; `verify` counts a claim as supported only when its source can show it.
- **Corrections do not reach the deliverables that carried the claim.** One corrected figure had to be fixed in an overview, a slide and its notes, the exported PDF, the published deck, two notes and a ticket, and a correction drafted for the client. A `correction` supersedes records only; nothing records which deliverables, recipients or tickets carried a claim. Fix: the `progress` record for a sent or delivered deliverable lists the claim ids it carries, its recipients and where it lives (path, published page, ticket); a correction lists the deliverables carrying the superseded id and drafts a correction for each recipient.
- **Deliverables and sources share one mapping.** Each deliverable lives in a dated output folder (433 files in all), with raw extracts, scripts, the agent's own status notes and slide sources side by side. Mapped as `source_roots`, the agent's earlier summaries become citable sources, so a finding can rest on the agent's own prose. The text the client saw is skipped: slide HTML (63 files), deck JSON, scripts, `.xlsx` and `.pdf` are not on the read list in SPEC.md section 8. Same root as "No home for drafts" above. Fix: a mapping for deliverable folders (written by the agent, searchable, never evidence) beside `source_roots` for raw material; read `.html` as text with the tags stripped.
- **The log's status section goes stale.** The project's `AGENTS.md` tells agents to add a dated timeline line and keep the log's "Now" section true after each task. Setup never edits `AGENTS.md` and records which rule wins in `work/ways-of-working.md`, which the block sends agents to only before writing to someone. `handoff` step 5 appends a dated entry but leaves "Now" alone, and no readable overview exists before `views build` in stage 3. Either "Now" goes stale or agents keep status in two places. Fix: let `handoff` write `work/views/overview.md` from stage 1; have setup offer to edit the user's losing line with their OK, or add a block line that points at "Decisions on instructions".
- **One handoff per session hides parallel workstreams.** The project runs five or more workstreams, often in parallel sessions. A handoff has one goal and one next action, and `brief` shows only the newest handoff in full, so the session that ended last hides the others. Task numbers (the highest `T-<n>` plus one) can collide between parallel sessions. Fix: a handoff carries `workstream_id`; `brief` shows the newest handoff of each active workstream in one line and the resumed one in full; check the task number again after writing.
- **`route` cannot name the tool, the account or the host.** The ticket system and a search console are reached through a browser extension on two browser profiles, picked by device id; analytics through an MCP server whose authorisation expired twice in eight days; decks are published as Claude artifacts that Codex cannot reach. `route` is `connector` or `on_screen`, and the block names open-cu, which could not reach Chrome in that project at the time. Fix: `route` per host, naming the tool and the account or profile; the last known state and its date on the system record; `brief` lists what is broken; operating tips go in the system record's body, and `capture` says so.
- **Host memory is a second store that only Claude reads.** The project has 15 notes in Claude Code's memory (the user's stances, data access, reporting preferences) that Codex cannot see. The inventory reads only the folder and the `CLAUDE.md` files above it, and Claude keeps saving new preferences to its memory. Fix: setup reads the host's memory for the folder as a source and proposes moving each note into `work/`; a block line sends preferences and stances to `work/`.
- **No place for what a reader knows.** The project's writing rules are spread over sections of `AGENTS.md` and a separate language file, and they start by naming the reader and what that reader already knows. `communication_doc` takes one file, and a person record holds channel and preferences but not background. Fix: `communication_doc` as a list; a person field for what they know and do not know; `verify` also runs the communication document's own checklist.
- **`verify` rewrites the user's draft.** The project's rule is to keep the user's structure, order and wording, and to offer additions separately. Step 4 of `verify` in SPEC.md section 9 rewrites the draft. Fix: return the claim table and line-level edits, and leave the structure alone.
- **Bookkeeping crowds the chat.** The block asks for a basis tag on every consequential statement, `capture` reports each save in a line, and the board is redrawn on every task change. In a session with many findings, that crowds the replies. Fix: basis tags stay in records; in chat, name the source and what it cannot show; one save line per step.
- **One record per claim splits an analysis.** A rank analysis with four related figures from one query becomes four findings. Fix: one finding per question answered, from one source and scope, with its table in the body.
- **Ask-first does not say how far an OK reaches.** The project's rule: an OK covers the change it was given for. Add that line to the `ways-of-working.md` defaults.
- **Setup on a real folder.** The folder has 549 files, 209 of them text files under 5 MB, beside a 1.4 GB analysis folder, 327 MB of compressed crawler logs and a 320 MB download. The smoke test above took 91 turns for five files. Fix: the inventory proposes excludes for large data folders before reading, and reads CSV and TSV as header, row count and period rather than in full.
